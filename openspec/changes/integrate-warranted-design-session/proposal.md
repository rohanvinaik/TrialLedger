# Proposal

## Why

Layer two already computes useful bounds, scoped consequences and rival interpretations, but the assistant still assembles some consequential handoffs. A fresh IPASS/ARCHER 1050 run exposes a bounded next step: make exception evidence, computation status, premise origin and revision dependencies reach the same computed decision list.

## What Changes

- Ship additive per-finding result metadata on existing reasoning operations first, then expose source-bound exception validation through the existing `design_bounds` CLI/MCP path.
- Prototype a layer-two session against the real IPASS/ARCHER requests before freezing its schema. Reuse existing consumers for an immutable snapshot, computed decision list and revision replay; do not make immediate public repairs depend on the session.
- Separate evidence uncertainty, unresolved translation and unfinished computation. Preserve existing logical decisions and name every cause instead of calling a solver limit an evidence gap.
- Represent exception intervals and their source-bound scope. Retain reported withdrawal counts separately from their proposed meaning as eligibility deviations. Validate a cap against applicable admitted evidence; never derive a ceiling from a reported floor, default to zero, or transfer a global exception to a particular PS/smoking subgroup.
- Retain possible failure targets and their narrowing warrants, including entry violations discovered after entry. Add bounded hypothetical evidence requests that distinguish declared surviving candidates without manufacturing observations or claiming exhaustive clinical design coverage.
- Evaluate declared population-binding candidates against existing count/scope constraints before asking for a judgment. Surviving arithmetic is compatibility, not identification.
- Project corpus features from referenced premises, deriving admission from their complete support and origin. A known user choice, a derived witness and a source-stated criterion are different objects even when each has known support.
- Replay all analyses from the revised snapshot initially. Return changed/withdrawn consequences and independent answers without relying on the assistant's memory or treating one minimal proof as every possible support.
- Persist executable clinical acceptance cases from the fresh pull. Keep the larger joint-feasibility, version-space, information-accounting and grammar extensions as sequenced follow-ons, with explicit prerequisites rather than unbuilt helpers.
- Add operation-aware information-conservation tests and bounded stage, decision-table and estimand contracts before completing session orchestration. Reuse the existing count, proposition and dependency engines; preserve per-check standing through their public consumers.
- Rotate clinical walkthroughs by design structure as well as disease and phase. Content-independent threshold tests do not establish coverage of escalation, withdrawal, crossover or cluster designs.

This is a deliberately bounded integration increment under `add-design-synthesis`, especially its tasks 7, 10 and 12. It does not finish that change or claim to classify every clause of an arbitrary protocol.

## Capabilities

### New Capabilities

None. The session integrates the existing symbolic trial-design capability.

### Modified Capabilities

- `symbolic-trial-design`: add computed session dispositions, scoped exception/binding handoffs, premise-backed consumer projections and revision replay while retaining the separate operations.

## Impact

Runtime work is confined to layer two, its CLI/MCP discovery and result/answer guides. Proposed owners are small modules for result semantics, exception bounds, session state, projections and orchestration; existing solvers remain authoritative for their supported questions. Layer-one retrieval, source records, reporting and workbook verification stay independent.

No new runtime dependency, database, solver replacement or source mutation is proposed for this first pass. Legacy direct reasoning requests remain supported. New session requests have a versioned closed schema; additive result metadata must not silently redefine old logical enums. README, AGENTS.md, SKILL.md and the consumer guide will describe only integrated capabilities after entry-point verification.

User-supplied screening-log ingestion remains a separate follow-on change. The present evidence-request
calculation produces investigation questions, not a screening-log importer or evidence of actual patients.

The investigation and exact receipts live in [evidence/workflow.md](evidence/workflow.md). Design decisions and follow-on boundaries belong in `design.md`; `tasks.md` records current implementation and verification progress.
