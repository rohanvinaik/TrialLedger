# Model-operated clinical workflow sanity check

This is an assistant action after each substantial coherent implementation change or documentation-focused change, using a different trial category for each substantial increment. A task group can constitute one coherent change; arbitrary grouping must not weaken this trigger. It is **not CI**, a new software gate, a scheduled job or an automatic clinical encoder. The founder requested it during this investigation on 2026-11-03. Apply it to this planning pass; place the full contributor procedure in DEVELOPING.md with a short development-only pointer from AGENTS.md.

## Purpose

Exercise the full available path from a sensible clinical question to evidence, typed reasoning, a meaningful revision and a usable decision handoff. Look for a promise the person cannot actually use, a missing consumer, a silently narrowed interpretation or information that became unavailable between stages. Passing a fixed teaching example does not satisfy the check.

## Procedure

1. **Choose the question before inspecting favorable records.** State an ordinary clinical-development task: population selection, treatment setting, comparator eligibility, assessment plan, analysis coverage or endpoint prerequisites. Define what a useful answer would look like. Rotate indication, phase and setting over successive passes; do not apply NSCLC rules to unrelated domains.
2. **Retrieve through TrialLedger.** Run the capability check when the environment changed, preview a coherent registry search, then gather the complete declared scope or a separately declared ID sample. Preserve exact requests, API scope, raw bodies and source identities. Never pretend a partial page is a complete search. If retrieval is unavailable, record the gap and use a declared retained-evidence fallback without calling it a fresh pull.
3. **Draw a fresh sample.** Record a random seed before reading the selected studies, sample from the retrieved identifier pool, and retain the pool and selection rule. Usually two or three trials suffice to exercise the workflow. The sample may be clinically heterogeneous; discover and report that rather than silently exclude awkward trials. A filtered replacement sample must retain the exclusions and reason. Randomness discourages fitting to familiar examples; it does not establish representative clinical validation.
4. **Read complete clinical units.** Read the selected studies' eligibility, relevant population/group definitions, measures, denominators and time/flow context. Ask what a sane trial designer would ask next. Numbers with matching names or totals are not automatically the same population, scale, event or endpoint. Preserve every material alternative and unexplained conflict.
5. **Use the full available system.** Compile the named direct source rules; inspect source checks; anchor relevant passages and proposed readings; use the applicable assertion, signal, interpretation, coordinate and corpus operations for this question. Do not call unrelated modules for coverage theater. State an unavailable integration as a finding, not a reason to supply the missing conclusion yourself. Read the actual prepared premises and full deciding result units. Retain complete request/result files.
6. **Revise one consequential premise.** Change a design choice, retract a binding, move a boundary or leave a disputed reading proposed. Re-run the actual operations. Check that the dependent conclusion changes or opens appropriately and independent information remains. The same source must not be rewritten to fit the new choice.
7. **Hand off the decision.** Present the clinical question, source evidence, exact conditional consequences, remaining decisions and evidence/translation/computation tasks. Verify that the person can tell which next action would help. A known restriction is not whole-patient eligibility; compatibility is not the true protocol; historical frequency is not a design obligation.
8. **File the findings.** Keep `question`, `scope`, `seed`, `pool`, `sample`, source identities, actual operations, changed premise, observed consequence and open issues. Classify each issue as a wiring defect, an unsupported capability, an unresolved clinical interpretation or an evidence gap. Link a concrete counterexample to its owner. Do not discard a failed sample or silently patch the evidence. Fix within scope or retain the finding for the next bounded change.

## Reporting

Before acquisition, use DEVELOPING.md's walkthrough-retention contract. Keep complete reviewable reasoning
inputs/results, the clinical handoff and source/version fingerprints in Git; preserve bulky complete raw
and workbook packets separately with verified checksums. A required snapshot inside a reasoning request
is not expendable duplication. Registry re-fetches do not reproduce historical bytes by timestamp alone.
Expanded authored prototypes remain reviewable. Do not use archival compression to conceal the code or
premise choices under review.

Give one short clinical walkthrough and the concrete new findings. Keep formal test results, mutation receipts and the model's interpretation distinct. No single pass certifies full-thesis validity; the repeated action tests whether the thesis continues to hold at the user-facing boundaries actually exercised.
